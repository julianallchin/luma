This page lists the main architectural choices in Luma and the reason for each.

## Groups instead of fixture references

A score that names fixture ids breaks when the rig changes. A score names
groups instead:

- A clip selection is the whole venue or a union of the venue's groups.
- Each venue defines its own groups of its own fixtures.

A selection holds group ids, not names, so renaming a group changes no score.
Changing the fixtures in a group changes what every clip that selects it
lights. See [Selection System](/docs/architecture/selection-system).

## One small graph per clip

Every clip owns one small graph of typed nodes: 19 kinds, one output node. A
value is typed, a choice is a setting, and anything that varies is a wire.
Looks such as chase, pulse and dissolve are preset graphs
(`backend/crates/patterns/src/presets.json`), not Rust kernels. An agent
writes the same graph as Python, with the same node names. The spec is
`docs/specs/clip-graphs.md`.

## Evaluation is a function of time

The evaluator computes a frame from the requested time only. It keeps no
playback history and has no fixed simulation rate. Because of this:

- Seeking and scrubbing give the same result as playback.
- The render loop, the visualizer and a batch render use the same code.
- A random choice comes from the seed, not from earlier frames.

## Musical time for clips

Clip start and duration are in beats. The beat grid of the track converts them
to seconds. A clip stays on the same beats when the beat grid changes. A beat
grid is never edited: a new analysis writes a new grid, and a score records
the grid it was written against.

## Unwired is not zero

A clip writes only what its output node drives. A color clip does not turn
off a movement from a lower clip. Alpha 0 is no clip: the light below shows,
in every blend mode.

## One SQLite database

All library data is in one `luma.db` file:

- It needs no database server.
- One pool serves all queries.
- Venue data and library data link through foreign keys, not through separate
  files.

## Rows as the sync unit

PowerSync syncs the app tables directly. There is no separate sync format and
no write server:

- Each domain writes its own tables in ordinary SQLite transactions.
- Two edits to one row merge per column.
- Postgres row-level security controls access.

## The server keeps what a device deletes

A device is a cache of live rows. The server is the permanent record:

- A delete on a device removes the row there. On the server it sets a flag,
  and the row leaves every other device.
- Ids are random, so a row keeps its id for good and inserting it again
  brings it back.
- The server logs every change to what people and agents made, with who made
  it.
- Analysis results are a cache. They are deleted for real and computed again
  from the audio.

Venues and their fixtures and groups sync like other rows. Venue members can
read and edit a shared venue. Where each universe goes is the local `dmx_routes`
table, because the DMX hardware belongs to one machine; it does not sync. See [Database](/docs/architecture/database).
